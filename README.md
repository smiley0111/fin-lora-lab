# fin-lora-lab

**标注口径类任务什么时候值得微调？** 用一个具体任务做对照实验：同一份提示词、同一份评测集，比较“只用提示词”“提示词加示例”“LoRA 微调”三种做法，以及 0.5B 微调后能否追上更大的模型。

任务是中文金融文本里的**负面金融主体识别**（FinCUGE 的 FINNSP）：给一段新闻或微博，找出被负面报道的机构（涉嫌诈骗、非法集资、逾期、跑路、被立案等），没有就回答“无”。“什么算负面主体”是标注方自己的口径，比如“小资钱包”要不要带上“P2P平台”、只是被提到的机构算不算，这些很难用提示词说清楚。

全部实验在一台没有 GPU 的笔记本上完成（i5-1145G7，4 核 8 线程，16GB 内存）。

## 结论

| 方法 | 实体 F1 | 精确率 | 召回率 | 完全正确 | 误报率 | 漏报率 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.5B 只用提示词 | 32.2% | 35.9% | 29.2% | 28.8% | 61.0% | 23.5% |
| 0.5B 提示词 + 3 个示例 | 4.6% | 27.5% | 2.5% | 45.6% | 8.7% | 93.4% |
| 1.5B 提示词 + 3 个示例（4bit） | 55.6% | 56.5% | 54.8% | 61.2% | 5.4% | 18.1% |
| 3B 只用提示词（4bit） | 57.4% | 58.6% | 56.3% | 61.8% | 10.8% | 9.7% |
| 3B 提示词 + 3 个示例（4bit） | 56.9% | 56.8% | 57.0% | 61.2% | 5.0% | 17.8% |
| 0.5B + LoRA，200 条训练 | 51.4% | 52.1% | 50.7% | 55.0% | 13.3% | 33.2% |
| **0.5B + LoRA，800 条训练** | **64.7%** | **67.9%** | 61.8% | **65.6%** | **4.2%** | 20.5% |
| 0.5B + LoRA 800 条 + 过滤原文没有的实体 | 66.1% | 71.4% | 61.5% | 67.8% | 4.2% | 20.9% |

测试集是 FINNSP 官方评测集的 500 条。误报率是“没有负面主体的文本里被报出了主体”的比例，漏报率是“有负面主体的文本里什么都没报”的比例。完整结果和错误类型分布见 [reports/results.md](reports/results.md)。

1. **800 条数据、CPU 上训练 112 分钟，0.5B 模型的 F1 从 32.2% 提到 64.7%，超过 3B 模型只用提示词的最好成绩（57.4%）。** 误报率 4.2%，是所有方法里最低的。
2. **数据量是关键。** 同样的配置，训练数据从 200 条加到 800 条，F1 从 51.4% 提到 64.7%，误报率从 13.3% 降到 4.2%。200 条时漏报还很多（33%），模型学会了“什么不算负面”，还没学全“什么算”。
3. **小模型只靠提示词分不清“提到”和“负面”。** 0.5B 零样本时，只要文本出现金融机构就报出来，“京东白条”“京东金融”的普通新闻也报成负面，误报率 61%。
4. **加示例反而让小模型更糟。** 0.5B 加了 3 个示例后，500 条里有 462 条回答“无”，F1 跌到 4.6%。它学到的是“保守地回答没有”，而不是判断标准。3B 加不加示例，F1 都在 57% 左右：示例只把它的误报压低了（10.8% → 5.0%），漏报却从 9.7% 升到 17.8%，两相抵消。
5. **抽取任务可以用“答案必须出自原文”兜底。** 微调后的 0.5B 有 5.2% 的实体在原文里找不到，多数是抄错字（“绿化贷”写成“绿意贷”）。一行规则把它们过滤掉，F1 再提 1.4 个百分点，召回率几乎不变。

**比较不完全对等的地方**：1.5B 和 3B 是 Ollama 的 4bit 量化版，0.5B 是 transformers 的 fp32 全精度。量化可能压低了 3B 的成绩，所以“0.5B 微调超过 3B”应理解为“超过本机能跑的 3B 量化版”。另外每组实验只跑了一次，没有多个随机种子，几个百分点以内的差别不一定稳定。

## 实验设计

### 数据（`src/finlora/data.py`）

- 来源：[FinCUGE-Instruction](https://huggingface.co/datasets/Maciel/FinCUGE-Instruction)（Apache-2.0）的 FINNSP 任务，训练集 4000 条，评测集 500 条。
- 原始数据同一任务有十几种指令写法和回答模板（“负面金融主体包含以下几个：……”“以上文本不存在负面主体。”……）。统一成一种提示词，输出统一成 `实体1;实体2` 或 `无`。所有方法用同一份提示词，结果才可比。
- 训练集里有 2 条和测试集文本相同，删掉了。训练集去重后再划出 200 条做 dev 集，训练中观察 loss 用。
- 输入截到 300 字，控制 CPU 上的计算量。测试集 500 条里有 53 条被截断。
- **标注噪声**：测试集有 17 条的标注实体在文本里找不到原样，其中 8 条是截断造成的，9 条是标注本身的问题（见下面的错误案例）。这部分任何方法都拿不到分，满分不可达。

### 训练（`src/finlora/train.py`）

- 基座 Qwen2.5-0.5B-Instruct，权重冻结；LoRA 加在注意力和 MLP 的 7 个投影层上，r=16、alpha=32，可训练参数 880 万，占 1.75%。
- **只对回答部分算 loss**：用 chat 模板分别生成“只有提示词”和“完整对话”两段，断言前者是后者的前缀，提示词部分的 label 设为 -100。否则模型会把大部分力气花在“背”固定的提示词上。
- **按长度分桶组 batch**：先按长度排序切 batch，再打乱 batch 顺序。CPU 上 padding 就是白算。
- 有效 batch 16（8 × 梯度累积 2），学习率 2e-4，5% warmup 后余弦衰减，1 个 epoch。
- 训练循环自己写，没用 `Trainer`，每一步做了什么都在代码里看得到。
- CPU 速度实测：关掉梯度检查点、batch 改为 8，比初始配置快约 20%；线程数 4 和 8 没有差别。0.5B 在 16GB 内存上不需要梯度检查点。

### 评测（`src/finlora/metrics.py`、`src/finlora/predict.py`）

- 实体级：每条样本的标注和预测都看成实体集合，比较前统一全半角括号和大小写，算 micro 精确率、召回率、F1。
- 样本级：只看“有没有负面主体”，算误报率和漏报率。风控里这两类错误的代价不同，单看 F1 看不出来。
- 幻觉率：预测出的实体里，原文根本没有的比例。
- 错误分类：正确、误报、漏报、实体边界不对、多找了、少找了、找错了、输出了原文没有的实体。
- 推理一律贪心解码（temperature 0）。few-shot 的 3 个示例从训练集里按固定规则挑选（短文本，有实体和无实体交替），每次实验都一样。

## 错误案例

**零样本把“提到”当成“负面”**，微调后不再误报：

> 近日，由京东金融携手 DT 加油、中石油浙江销售公司合作推出的不下车加油移动支付服务……
>
> 标注：无　0.5B 零样本：京东金融　3B：无　0.5B + LoRA：无

**实体边界：标注只要主体名称，不要修饰语**。3B 带上了“上市公司”“网贷平台”，微调后学会了口径：

> 上市公司泛华金融于国企中国对外经济贸易信托有限公司合作放高利贷……
>
> 标注：泛华金融；中国对外经济贸易信托有限公司　3B：上市公司泛华金融；中国对外经济贸易信托有限公司　0.5B + LoRA：与标注一致

> #小资钱包[超话]#北京资易贷公司（小资钱包网贷平台）负责人潘博艺李兆民失联……
>
> 标注：小资钱包；资易贷　3B：北京资易贷公司；小资钱包网贷平台　0.5B + LoRA：与标注一致

**微调后的小模型会抄错字**，这类错误用“必须出自原文”就能拦掉：

> ……关于绿化贷、壹佰金融涉嫌非法吸收公众存款案件的最新进展……
>
> 标注：绿化贷；壹佰金融　0.5B + LoRA：**绿意贷**；壹佰金融

**有些错误其实是标注的问题**：

> {IMG:1} 我和我的一万只爬宠
>
> 标注：钱宝网（文本里没有）　0.5B 零样本、3B、0.5B + LoRA：都回答无

> ……大连P2P平台小满金服发布良性退出公告称，即日起，停止发布新项目……
>
> 标注：东朗理财（文本里没有）；小满金服　3B：小满金服　0.5B + LoRA：小满金服；**大连金服**（自己拼出来的）

逐条对比 3B 只用提示词和 0.5B + LoRA（800 条）：LoRA 对、3B 错的有 65 条，3B 对、LoRA 错的有 46 条。两者错的地方不完全重合，3B 的强项是读懂长文本里的事件，LoRA 的强项是口径和边界。

## 复现

需要 Python 3.10–3.13 和 [uv](https://docs.astral.sh/uv/)；对比实验还需要本地 [Ollama](https://ollama.com/)，并拉取 `qwen2.5:1.5b`、`qwen2.5:3b`。

```powershell
uv sync --extra dev

# 1. 数据：下载 FinCUGE-Instruction 的两个 parquet 到 data/raw/（train.parquet、eval.parquet），然后
uv run python -m finlora.data

# 2. 模型：下载 Qwen2.5-0.5B-Instruct 到 models/Qwen2.5-0.5B-Instruct/（ModelScope 或 HuggingFace）

# 3. 全部实验（CPU 上约 4–5 小时；已有结果的步骤会跳过）
powershell -ExecutionPolicy Bypass -File run_all.ps1

# 4. 汇总
uv run python -m finlora.report
uv run python -m finlora.postfilter lora-0.5b-n800

uv run pytest
```

单独跑某一步：

```powershell
uv run python -m finlora.train --name lora-n800 --n-train 800
uv run python -m finlora.predict --name lora-0.5b-n800 --adapter runs/lora-n800/adapter
uv run python -m finlora.predict --backend ollama --model qwen2.5:3b --name ollama-3b-zeroshot
```

LoRA 适配器（每个约 34MB）没有放进仓库，用上面的命令可以重新训练；每次训练的超参数、loss 曲线和耗时在 `runs/*/summary.json` 和 `runs/*/train_log.jsonl`。

## 过程中遇到的问题

- **公司网络拦截 TLS**：uv 要设 `UV_NATIVE_TLS=1` 才认系统证书；Python 下载模型同样失败，改用 Windows 自带的 `curl.exe`（走系统证书库）。
- **下载源速度差两个数量级**：hf-mirror 只有约 80KB/s，ModelScope 直链有 14–20MB/s。
- **两个下载进程同时写一个文件**：之前被中断的 curl 没有真正退出，和新下载一起写 `model.safetensors`，把文件写坏了。加载权重时校验失败才发现，杀掉所有 curl 重新下载，并核对参数量是 4.94 亿。
- **数据整理里的一个自己的 bug**：起初把标注实体里的全角括号转成了半角，原文却还是全角，导致很多标注实体“在原文里找不到”。改成保留实体原样、比较时两边用同一个规则统一括号。
- **PowerShell 5 读不了无 BOM 的 UTF-8 脚本**：`run_all.ps1` 里的中文会被读成乱码导致语法错误，要存成带 BOM 的 UTF-8。
- **杀毒软件和降频抢 CPU**：长时间训练时每条样本的耗时是短时基准测试的 2 倍多，800 条训练从预计的 50 分钟变成 112 分钟。

## 局限

- 只有一个任务、一个基座模型、一组超参数，每组只跑了一次。
- 没有试更多训练数据（训练集还有约 3000 条没用）、更多 epoch 或不同的 LoRA rank。按 200 → 800 条的趋势，继续加数据大概率还能涨。
- 3B 对比用的是 4bit 量化版，没有在同等精度下比较。
- 测试集有约 3% 的标注噪声，几个百分点以内的差别要谨慎解读。
